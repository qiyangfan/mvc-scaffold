# ADR-0006: 主键改用 UUID v7（应用侧生成，废弃自增 ID 回填）

## 状态

已接受 (Accepted) — 2026-10

## 上下文 (Context)

脚手架原实现用数据库自增主键，由此派生出一整套"补丁式"约定：

| 现象 | 根因 |
| --- | --- |
| `EmployeeServiceImpl.createEmployee()` 先 `insert` 拿自增 ID，再 `updateEmpNo(...)` 回填工号 | 业务编号依赖数据库自增序列，必须二次写库 |
| Mapper 的 `insert` 带 `useGeneratedKeys="true" keyProperty="id"` | 主键由数据库分配，应用侧不知道 |
| Jackson 全局 `Long → String` 序列化 | 64 位自增/雪花 ID 出到前端丢 JS 精度 |
| 多实例部署要另配雪花/号段 | 自增本身不保证多实例唯一 |

自增主键还顺带暴露业务量级（竞品可据 ID 增量估算单量），分库分表时也是长期负担。

## 决策 (Decision)

1. **主键统一为 UUID v7 字符串**，由 `common/support/Ids.newId()` 在 Service 插入前生成（应用侧身份）；
2. `EmployeeMapper.insert` 去掉 `useGeneratedKeys`，删除 `updateEmpNo`
   方法与对应 XML——**一次 insert 完成落库**；
3. 工号由主键派生：`EMP` + UUID v7 去横线后的前 12 位十六进制（大写）；
4. 分页上限收敛为 `PageQuery.MAX_PAGE_SIZE` 单一事实源，校验注解与任何兜底钳制引用同一常量。

## 为什么工号取前 12 位十六进制

UUID v7 的高 48 位就是毫秒时间戳，十六进制表示正好是去横线字符串的前 12 位。因此工号：

- 随时间递增、可排序；
- 不暴露自增序列量级；
- 与主键一一对应，排查问题时可直接互推。

## 为什么是 UUID v7 而不是 UUID v4 / 雪花 / 号段

| 方案 | 结论 |
| --- | --- |
| UUID v4 | 完全随机，主键索引页分裂严重，大表写入性能差 |
| 雪花 / 号段 | 需要额外基础设施（worker id 分配、号段服务），与"轻量脚手架"目标冲突 |
| **UUID v7** | 时间戳在高 48 位，**字典序≈时间序**，B-tree 友好；应用侧生成零依赖；`Ids` 用 rand_a 做同毫秒递增序号，进程内严格单调 |

## 后果 (Consequences)

### 正向收益

- 创建路径少一次 UPDATE：从"insert + 回填"两次写变成一次写；
- 多实例唯一性天然成立，不再需要雪花/号段基础设施；
- 主键对外即字符串，精度问题在主键层面消解；
- 排序语义明确：`ORDER BY gmt_create DESC, id DESC`，不依赖 ID 文本序。

### 代价与缓解

- 存储 36 字节 vs 8 字节：可接受；若未来需压缩，改 `BINARY(16)` 是 Mapper 层局部改动；
- `Ids` 有一个带锁的静态临界区：只保护毫秒戳+序号两个 long 赋值，纳秒级；实测万次生成无重复；
- 存量库迁移需新增字符串主键列并回填：新项目无此问题。

## 备选方案（已否决）

- 保留自增 + 回填工号：多一次写、多一份并发窗口，否决；
- 只用 UUID v4：索引写入劣化，否决；
- 引入雪花算法：为一个脚手架引入号段/worker 基础设施，过度设计，否决。
